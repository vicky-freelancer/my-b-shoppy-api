# Schema 001 review and rollback

`001_production_draft.sql` is a fresh-schema review draft, not permission to install. It has not been executed against MariaDB. The catalog portion derives from the revised isolated fixture; payment tables are new and unverified. No schema ledger is created or asserted. Do not deploy until an explicitly authorized isolated MariaDB 11.8.9 installation and integration/concurrency tests pass and the DDL is independently reviewed.

Before any later installation approval: re-check target identity, privileges, schema emptiness, backup/restore capability, and version/checksum. MariaDB DDL implicitly commits; an interrupted run may leave some tables installed. Stop on the first error, preserve the exact error and object inventory, and do not rerun blindly. No seed data or admin account is included. Application connection guards and checkout remain disabled.

Rollback requires separate explicit authorization and a verified backup. If anything has written to these tables, do not drop them: stop writers and payment processing, preserve and reconcile orders, inventory, webhook events and provider state, and prepare a reviewed restoration or forward-fix plan. If a fresh install failed before any data was added, an authorized operator may inspect the exact target and objects, verify they are empty, then approve a separately prepared reverse-dependency removal plan. Never disable foreign-key checks or remove an entire database as a shortcut. DDL is not transactionally reversible. Verify metadata and restore application state after any approved recovery.

Checkout safety depends on more than this schema. The prototype is not connected to the API routes, rejects live mode, and assumes a durable schema that has not been tested. The webhook handler accepts event IDs up to 256 bytes and event types up to 128, while `CheckoutService.persistEvent` rejects lengths over 128 and 64 respectively. Reconcile these limits and duplicate-key races before wiring the adapter. Its reservation release/reconciliation and unknown provider outcomes also require tested operational procedures. Reservation quantities matching order line quantities, receipt-to-attempt provider identity, aggregate order totals, and atomic stock/receipt/order transitions require application enforcement and concurrency tests; the DDL alone does not guarantee them. Confirm check constraints and required FK/index behavior on the actual MariaDB version. No live provider calls are authorized.
